# 多应用运行时与资源治理 v0.1

状态：设计与验收约束，尚未实现或基准测试。本文细化 ARCHITECTURE、PLUGIN-SPEC 的运行语义；参数均为待原型验证的初始策略，不是性能承诺。

## 1. 分开管理四类对象

| 对象 | 唯一标识 | 生命周期 |
| --- | --- | --- |
| 已安装插件 | pluginId + version | 安装、启用、禁用、升级、卸载 |
| 应用会话 | sessionId | 打开、切换、挂起、恢复、关闭 |
| 后台执行器 | pluginId + generation | 按需启动、工作、空闲回收、崩溃 |
| 后台任务 | jobId | 入队、执行、等待、恢复、成功或失败 |

标签存在不代表页面或后台进程存在；关闭页面不自动取消持久任务。安装十个插件不会启动十个后台进程。工作台关闭与最小化是不同操作。

## 2. 主体如何识别插件

用户选择安装包 → 暂存解包 → 校验 manifest/schema/入口路径/权限/API 兼容/文件摘要 → 展示权限 → 数据迁移 → 原子切换版本目录 → 提交安装注册表 → 更新导航及能力索引。

注册表记录 pluginId、version、安装目录、manifest 摘要、启用状态、授权和安装结果。磁盘目录和数据库不能靠单一事务原子提交：使用安装日志与 staging 状态，启动时完成或回滚未完成步骤。未注册目录不自动执行；用户手工复制文件不能绕过安装验证。开发加载入口必须显式开启并标记。

启动只读已启用插件的已验证元信息，注册菜单、页面和查询描述，不执行所有插件入口。首次 openView、executeCommand、query 或 job 事件再按需激活对应能力。插件 ID 在安装时绑定到 IPC 发送方，不采用消息自报身份。

所有 view、command、query、jobType 的 ID 以 pluginId 命名空间隔离；注册冲突拒绝安装。一个插件可以声明多个应用入口，入口 ID 和 pluginId 分开存储。更新不改变稳定 ID。

## 3. 同时打开与切换应用

第一版允许多个逻辑会话/标签，同时只有一个可见的业务页面；真正并排显示属于后续分屏功能。宿主侧栏、标签栏始终存在。

每个会话保存 pluginId、viewId、resourceId、route、标题、页面状态版本、布局状态、最后访问时间、草稿引用、数据修订号。打开同一 viewId + resourceId 默认复用会话；插件显式支持 multi-instance 才允许新建副本。多窗口写同一记录通过 revision 乐观锁检测冲突，不静默覆盖。

首选 WebContentsView 承载隔离页面原型；必须验证原生视图层叠、焦点、缩放、宿主全局弹层和无障碍。宿主弹层不能假设 DOM z-index 能覆盖原生子视图；实现统一遮盖/可见性协调或独立宿主浮层。验证失败再评估容器方案，保持会话协议不变。

插件使用独立 origin 与会话 partition，禁用 Node 集成并启用隔离和 sandbox。Electron/Chromium 实际进程分配不保证与会话一一对应；安全与资源统计不能依赖该假设。

## 4. 页面状态机

```text
closed → loading → visible ⇄ hidden-warm
                     ↑          ↓
                  restoring ← suspended
loading / visible / hidden-warm → crashed → restoring 或 closed
```

- visible：当前交互页面。
- hidden-warm：页面暂留内存，取消非必要动画、观察器、订阅和轮询；宿主推送 visibility 事件。保持 backgroundThrottling 默认开启，但不将它视为释放内存或任务调度保证。
- suspended：草稿及小型 UI 快照已持久化，销毁页面 webContents；标签和会话记录保留。
- restoring：重新创建页面，校验状态版本，恢复草稿、路由、选择和滚动位置，并重新查询最新业务数据。

挂起协议：宿主发送 prepareSuspend(requestId) → 页面停止新编辑/等待在途持久化 → 返回 durable revision 与可序列化快照 → 宿主持久化确认 → 检查请求 generation 和当前可见状态 → 销毁页面。用户在途中切回时取消挂起，避免销毁刚恢复的页面。超时或保存失败不强行销毁带未保存内容的页面，显示占用原因。

快照只存路由、筛选、选择、滚动和草稿 ID，建议上限 256 KiB；正文、图片和大型表格不进入快照。持续自动保存草稿，不能只依赖关闭回调。所有 await 后重新检查 generation，避免过期响应覆盖当前会话。

从窗口移除视图并不等于释放 webContents；释放路径必须显式关闭/销毁内容、解除事件、MessagePort 和宿主引用。确认退出前处理 beforeunload/未保存内容，禁止绕过保存协议强制回收。

## 5. 后台等待与任务执行

界面只提交任务，不承担长任务执行。宿主持久化任务记录：jobId、pluginId、pluginVersion、jobType、参数引用、状态、进度、检查点、重试次数、nextRunAt、lease、idempotencyKey。

```text
queued → running → succeeded / failed / canceled
             ├→ waiting-io → running
             ├→ waiting-user → queued
             ├→ retry-scheduled → queued
             └→ interrupted → queued 或需人工处理
```

- 等待 I/O 用异步事件，不忙循环；活跃网络请求暂占执行器和 I/O 配额，不占 CPU 重任务配额。
- 等用户、长时间重试和预约：持久化上下文后释放执行槽，空闲执行器可退出；恢复时新建执行器，从检查点继续，不保存 JavaScript 调用栈。
- 关闭页面：任务继续，结果写入数据库和通知中心。
- 取消任务：先协作取消并回滚或完成事务；超时标记异常。不能在已提交外部副作用后声称已撤销。
- 实际进程退出/断电：任务标记 interrupted；只自动恢复声明可恢复且幂等的任务。网络副作用不保证 exactly-once，使用幂等键和结果核对；未知结果需人工确认。
- 升级/禁用插件：先禁止新任务，排空或取消现有任务后切换。未完成任务绑定版本，保留所需旧包，禁止在新版本直接解释旧检查点。

第一版可信后台采用按需 utilityProcess，每个活跃插件最多一个执行器，全局最多两个执行器；同插件默认串行。排队采用插件间轮询，交互只读查询可优先但设连续次数上限避免饿死任务。调度时区分 CPU 和 I/O 配额；CPU 重任务默认最多一个。长等待必须让出执行器，避免两个等待任务阻塞所有查询。

utilityProcess 有 Node 能力，不是第三方代码安全沙箱；内存阈值是监测和回收策略，不是硬隔离。执行器空闲 60 秒后回收；确有常驻连接需求需独立的后台权限和明确 UI 提示，第一版不提供。

## 6. 窗口关闭、休眠、恢复

第一版默认关闭窗口即退出应用，有任务或未保存内容时展示“继续运行 / 取消并退出”及任务清单；不能默默丢弃。最小化继续运行。后续托盘常驻必须明确开启。

真正退出时停止接单，保存草稿、检查点和会话，释放执行器、数据连接和视图。不可中断任务说明风险；系统强制结束仍可能发生，靠恢复协议处理。系统睡眠期间不承诺后台任务继续，唤醒后重建连接、核查租约及已错过调度。

## 7. 内存治理

初始默认：最多保留当前页加两个 warm 页面；隐藏超过 5 分钟可挂起；超出缓存上限优先回收最近最少使用且已保存的隐藏页。这些限制针对渲染页面，不限制已打开逻辑标签数。固定标签不等于常驻内存。

总进程树内存软预算的初始候选为 min(1 GiB, max(384 MiB, 物理内存 × 10%))；需在 8/16 GiB Windows 机器上实测修订，绝不承诺实际一定低于预算。按去重后的 OS PID 汇总 private bytes，单独观察 working set、CPU 和 GPU；不能仅看 JS heap，也不能把共享内存重复相加当成准确总量。可见页面单独就可能超预算，此时限制大资源、提示而非强杀编辑页面。

内存持续三个采样周期（建议每 10 秒一次）超预算时：清理宿主缓存 → 挂起最旧安全隐藏页 → 回收空闲执行器 → 降低任务并发/暂停新重任务 → 展示资源占用。下降到预算 80% 以下且持续稳定后恢复并发，避免抖动。不能反复自动重载故障插件。

具体优化：

- 插件按需加载；安装状态不加载 React/编辑器运行代码。
- 列表虚拟化、查询分页、增量更新，避免一次读入全部数据。
- 图片缩略图和按需解码；大文件流式读取，IPC 传引用或分块，不把整个文件转 base64 多次拷贝。
- 缓存有容量、TTL 和清理接口；销毁页面释放订阅、计时器、对象 URL、MessagePort。
- 数据查询限条数、响应大小和超时；后台批处理分批提交进度。
- 使用有界队列和背压；通知进度合并推送，避免每条记录发送 IPC。

## 8. AI 访问不唤醒 UI

已授权查询路由到数据服务或按需后台查询处理器，页面处于 suspended 不影响读取持久数据；不读取尚未保存的输入框。需要自定义处理器时经过同一任务调度器。不存在后台实现的 UI 专属查询不得标为 aiReadable。

## 9. 诊断与验证

设置增加“运行状态”：插件、逻辑会话、页面状态、任务数、进程级占用、最近故障和释放入口；进程共享时标注共享，避免伪造精确插件归因。自动重启最多短时间内两次，继续失败则隔离并提示。

必须完成：

1. 安装 30 个插件，仅启用元信息，不出现 30 个渲染页或执行器。
2. 打开 10 个轻量会话，稳态最多 3 个驻留页；草稿未保存的例外可见且有原因。
3. 切换 100 次并重复挂起恢复；快照、草稿、滚动及任务状态一致。
4. 切回与挂起同时发生、窗口退出与保存同时发生，验证 generation 防竞争。
5. 后台任务运行时关闭其页面，任务继续；禁用插件、重启和断电模拟后状态正确。
6. 两个等待用户任务不阻塞第三个任务；取消、超时、重复执行和版本升级有确定结果。
7. 模拟内存压力时不丢编辑数据，回收后释放引用；循环后内存达到平台而非持续线性增长。
8. 将渲染页/执行器主动终止，主窗口保持可用；AI 查询无需打开插件页面。

记录 Windows 版本、Electron 版本、硬件、构建模式、数据量、进程树内存时间序列、恢复延迟 P50/P95。原型初始体验目标为 warm 切换 P95 < 200ms、轻量页恢复 P95 < 1s，均需实测后确认。
